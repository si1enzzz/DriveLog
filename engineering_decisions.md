# Дневник инженерных и архитектурных решений (Architecture Decision Records)

> Этот документ — твой «дневник архитектора». Здесь зафиксированы ключевые инженерные решения проекта **AutoCare Tracker**: **что** мы выбрали, **почему** именно это, и **какие альтернативы** мы отбросили. Это готовый конспект ответов на вопросы приёмной комиссии университетов (HIT / NUAA) и технического собеседования.

### ADR 001: Выбор архитектурного паттерна MVVM вместо Code-Behind

* **Контекст:** Нам нужно разрабатывать интерфейс приложения, где данные (пробег, цены, записи о ремонтах) постоянно меняются.
* **Рассматриваемые варианты:**
  1. *Code-Behind* (старый подход: писать обработчики кликов прямо в `MainWindow.axaml.cs`, обращаясь к элементам через `myTextBox.Text`).
  2. *MVVM (Model - View - ViewModel)* — разделение на три независимых слоя через Data Binding.
* **Решение:** Выбран **MVVM** с библиотекой `CommunityToolkit.Mvvm`.
* **Почему (Trade-offs):**
  - **Separation of Concerns (Разделение ответственности):** Вся бизнес-логика (расчёт сумм, валидация пробега) живёт в `MainViewModel.cs` и не зависит от кнопок и цветов.
  - **Тестируемость (Testability):** Мы можем написать автоматические unit-тесты на класс `MainViewModel`, даже не запуская само графическое окно.
  - **Кроссплатформенность:** Модели и логика остаются на 100% общими для Windows, Android и iOS. Меняется только XAML-разметка.
* **Минусы решения:** Чуть больше файлов на старте (нужны отдельные классы ViewModel), требует понимания Data Binding.

### ADR 002: Использование ObservableCollection<T> вместо List<T>

* **Контекст:** Хранение динамического списка выполненных работ по автомобилю.
* **Рассматриваемые варианты:**
  1. `List<ServiceRecord>` — стандартный список C#.
  2. `ObservableCollection<ServiceRecord>` — реактивная коллекция из пространства `System.Collections.ObjectModel`.
* **Решение:** Выбран **`ObservableCollection<ServiceRecord>`**.
* **Почему (Trade-offs):**
  - Обычный `List<T>` хранит данные молча. Если мы вызовем `list.Add(newRecord)`, интерфейс Avalonia не узнает об этом и экран останется прежним.
  - `ObservableCollection<T>` реализует интерфейс `INotifyCollectionChanged`. При добавлении или удалении элемента коллекция автоматически генерирует событие `CollectionChanged`. Движок Avalonia перехватывает его и мгновенно дорисовывает карточку на экране без ручного обновления окна.

### ADR 003: Вычисляемые свойства «на лету» (TotalCost и TotalSpent)

* **Контекст:** Подсчёт стоимости ремонта (деталь + работа) и общего бюджета на обслуживание.
* **Рассматриваемые варианты:**
  1. Создать отдельную колонку в базе данных и вручную складывать `PartCost + LaborCost` при каждом вводе.
  2. Использовать геттеры только для чтения (Expression-bodied properties): `public decimal TotalCost => PartCost + LaborCost;`.
* **Решение:** Вариант 2 — вычисление на лету.
* **Почему (Trade-offs):**
  - **Single Source of Truth (Единый источник правды):** Невозможно получить ошибку рассинхронизации, когда деталь стоит 2000, работа 1000, а в графе «Итого» по ошибке записано 5000. Сумма всегда гарантированно точна.
  - Использование **LINQ** (`Records.Sum(r => r.TotalCost)`) делает код лаконичным и декларативным.

### ADR 004: Защита от NullReferenceException и дефолтные значения

* **Контекст:** Поля модели данных `ServiceRecord` могут быть не заполнены пользователем.
* **Решение:** Все строковые свойства инициализируются значениями по умолчанию (`string.Empty` или понятными плейсхолдерами, например `ServiceName = "Сам в гараже"`).
* **Почему (Trade-offs):**
  - В C# 8+ включен `Nullable Reference Types`. Если переменная строки не помечена знаком `?`, она не имеет права быть `null`.
  - Значения по умолчанию защищают приложение от самого частого краша в мире (`NullReferenceException`), если пользователь пропустил необязательное поле ввода.

### ADR 005: Стратегия масштабирования при росте базы (50,000+ записей)

* **Контекст:** Что делать, если история обслуживания автомобиля или таксопарка разрастётся до десятков тысяч записей.
* **Решение (Архитектурный план):**
  1. **UI Virtualization:** Переход от простого `ItemsControl` к виртуализированным контейнерам (например, `ListBox` или `ItemsRepeater` с `VirtualizingStackPanel`), которые создают в оперативной памяти только 10–15 видимых карточек и переиспользуют их при прокрутке.
  2. **Database Pagination (Lazy Loading):** Выборка из локальной SQLite порциями по 20–50 штук через SQL команды `LIMIT/OFFSET` (LINQ `.Skip().Take()`), чтобы не выгружать мегабайты данных в оперативную память устройства.

### ADR 006: Шейдерный эффект Liquid Glass (LiquidGlassAvaloniaUI + SkiaSharp)

* **Контекст:** Реализация эффекта жидкого стекла с оптическим преломлением (Refraction) и хроматической аберрацией.
* **Решение:** Подключена библиотека `LiquidGlassAvaloniaUI` (локальный пакет `.nupkg`).
* **Как это работает:**
  - В отличие от простой полупрозрачности CSS, `LiquidGlassSurface` использует графический движок **SkiaSharp** и шейдеры **`SKRuntimeEffect`**.
  - Контрол захватывает фоновые пиксели позади себя, применяет блюр (Backdrop Blur), рассчитывает угол преломления света линзой (`RefractionAmount`) и накладывает световой блик на скруглённых краях (`HighlightOpacity`).
* **Где применили:** Шапка выбора авто, карточка машины, форма ввода и карточки истории.

### ADR 007: Поддержка нескольких автомобилей (Multi-Vehicle Architecture)

* **Контекст:** В семье или у пользователя может быть 2+ автомобиля, либо смена машины со временем.
* **Решение:**
  - Создана модель `Vehicle` (Id, Name, CurrentMileage, `ObservableCollection<ServiceRecord> Records`).
  - У каждого автомобиля — своя изолированная история замен и свой подсчёт расходов `TotalSpent`.
  - При переключении через `ComboBox` вся статистика и лента мгновенно переключаются на выбранную машину.
  - Добавлена валидация: удаление блокируется, если в гараже остался только один автомобиль.
