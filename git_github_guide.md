## 1. Почему программисты не могут жить без Git

Вспомни, как обычно выглядит папка школьника или студента перед сдачей курсовой:
```
Курсовая_финал.docx
Курсовая_финал_исправленная.docx
Курсовая_финал_точно_последняя.docx
Курсовая_финал_переделал_ночью_копия(2).docx
```

Если так писать программы, наступает катастрофа:
1. **Случайная поломка:** Вчера приложение работало, сегодня ты дописал 10 строчек, всё сломалось и не запускается. Что именно ты изменил? Как вернуть рабочую версию? Без системы контроля версий придётся судорожно жать `Ctrl + Z` или переписывать всё заново.
2. **Командная работа:** Два разработчика одновременно редактируют файл `MainViewModel.cs`. Один скинул файл другому в Telegram — чьи изменения победят? Изменения первого просто перезапишутся и пропадут.
3. **Параллельные эксперименты:** Ты хочешь попробовать переписать расчет одометра на моточасы. Но боишься сломать старую рабочую версию по километрам. Как безопасно поэкспериментировать?

**Git решает все эти проблемы:**
* Это **машина времени**: сохраняет контрольные точки (коммиты) проекта. Ты можешь в любой момент за 1 секунду прыгнуть в прошлое на любую дату и посмотреть, как выглядел код.
* Это **черная коробка самолёта**: видно автора каждой строчки кода, дату изменения и комментарий — *зачем* это было сделано.
* Это **песочница для экспериментов**: можно создать параллельную ветку, попробовать безумную идею; получилось — влить в основной проект, не получилось — удалить ветку без единого следа.

## 2. В чём разница между Git и GitHub

Очень частая путаница у новичков:
* **Git (Гит)** — это **программа-инструмент**, установленная на твоём компьютере (консольная утилита). Она работает локально в папке проекта даже **без интернета**. Создана в 2005 году Линусом Торвальдсом (создателем ядра Linux).
* **GitHub (Гитхаб)** — это **облачный сайт-сервис** (принадлежит Microsoft). Это хостинг для Git-репозиториев, социальная сеть для программистов, портфолио разработчика и система управления проектами.

> **Аналогия:**
> * **Git** — это текстовый редактор Microsoft Word на компьютере.
> * **GitHub** — это облачный диск Google Drive или Яндекс.Диск, куда ты загружаешь файлы, чтобы поделиться ими с миром.
>
> *(Кстати, вместо GitHub есть и другие облачные сервисы: GitLab, Bitbucket, российский GitFlic, но мировой стандарт — именно GitHub).*

## 3. Внутреннее устройство Git: три зоны

Чтобы понимать Git и никогда не путаться в командах, нужно понять его главную ментальную модель. Внутри Git файлы всегда находятся в одной из **трёх зон**:

```
 ┌──────────────────────┐         git add          ┌──────────────────────┐        git commit        ┌──────────────────────┐
 │  Working Directory   │  ────────────────────►   │    Staging Area      │  ─────────────────────►  │  Local Repository    │
 │   (Рабочая папка)    │                          │   (Индекс / Сцена)   │                          │ (История коммитов)   │
 └──────────────────────┘                          └──────────────────────┘                          └──────────────────────┘
     Твои файлы на                                    Отобранные файлы,                                Постоянная база данных,
    диске (D:\...), где                               готовые попасть в                                  «слепок» проекта
     ты пишешь код                                    следующий снимок                                   на века (.git)
```

### Наглядная аналогия: «Посылка на почте»
1. **Working Directory (Твоя комната):** Ты собираешь посылку другу. На столе лежат 10 разных вещей: книги, свитер, кружка, фантики от конфет.
2. **Staging Area / Index (Коробка посылки):** Ты берешь только книгу и свитер и аккуратно кладешь их в почтовую коробку. Фантики оставляешь на столе. Команда `git add` — это процесс укладывания нужных файлов в коробку.
3. **Local Repository (Запечатанная посылка с накладной):** Ты закрываешь коробку скотчем, ставишь печать и наклеиваешь ярлык с надписью: *«Подарок на день рождения: свитер и книга»*. Команда `git commit` навсегда сохраняет этот снимок в историю.

## 4. Первоначальная настройка Git на компьютере

После установки Git нужно один раз представиться системе, чтобы Git знал, чьим именем подписывать коммиты.

Открой терминал (PowerShell или Git Bash) и выполни:

```bash
# 1. Твое имя или никнейм (будет видно в истории коммитов)
git config --global user.name "Timur"

# 2. Твоя электронная почта (ВАЖНО: укажи ту же почту, на которую зарегистрирован аккаунт GitHub!)
git config --global user.email "your_email@gmail.com"

# 3. Название главной ветки по умолчанию (в современном мире принято 'main', а не старое 'master')
git config --global init.defaultBranch main

# 4. Корректная обработка окончаний строк для Windows (CRLF -> LF)
git config --global core.autocrlf true
```

Проверить настройки:
```bash
git config --list
```

## 5. Базовый ежедневный цикл работы (Workflow)

Вот 5 команд, которыми программисты пользуются 90% рабочего времени:

### Шаг 1. Превратить папку в Git-репозиторий (`git init`)
Зайди в терминале в папку своего проекта:
```bash
cd "D:\projects\antigravity\app to drivers"
git init
```
*Что произошло?* Git создал скрытую папку `.git`. Теперь он тайно следит за всеми файлами в этой директории. Пока папка `.git` существует — вся история проекта жива.

### Шаг 2. Проверить статус (`git status`)
**Это главная команда.** Вызывай её каждый раз, когда сомневаешься:
```bash
git status
```
Git покажет:
* **Красным цветом (Untracked / Modified):** файлы, которые ты изменил в рабочей папке, но ещё не добавил в коробку (Staging).
* **Зеленым цветом (Changes to be committed):** файлы, которые уже лежат в коробке и готовы к коммиту.

### Шаг 3. Добавить файлы в индекс (`git add`)
```bash
# Добавить конкретный файл:
git add Vehicle.cs

# Или добавить ВСЕ измененные и новые файлы разом:
git add .
```

### Шаг 4. Зафиксировать снимок (`git commit`)
```bash
git commit -m "feat: add engine hours calculation logic"
```
Флаг `-m` означает "message" (сообщение). Ты запечатал посылку и дал ей понятное имя.

### Шаг 5. Посмотреть историю (`git log`)
```bash
# Полный лог со всеми деталями
git log

# Удобный компактный вид в одну строчку:
git log --oneline --graph --decorate
```

## 6. Искусство коммита: Conventional Commits

Главная ошибка новичков — писать сообщения вроде:
❌ `git commit -m "update"`  
❌ `git commit -m "fixed bug"`  
❌ `git commit -m "asdfgh"`  
❌ `git commit -m "ура заработало"`  

Приёмная комиссия университета или тимлид на работе сразу поймут, что перед ними любитель. Профессионалы используют стандарт **Conventional Commits**:

Каждое сообщение состоит из **типа** и **краткого описания на английском языке**:

| Префикс | Когда используется | Пример |
|---|---|---|
| `feat:` | Новая фича / функциональность | `feat: implement odometer daily rate calculation` |
| `fix:` | Исправление бага или ошибки | `fix: prevent negative mileage input on calibration` |
| `refactor:` | Переработка кода без изменения логики | `refactor: extract math formulas into MaintenanceService` |
| `ui:` / `style:` | Изменения внешнего вида XAML | `ui: redesign vehicle card with rounded borders and badges` |
| `docs:` | Документация, README, комментарии | `docs: add architecture explanation and formula formulas to README` |
| `test:` | Добавление или исправление unit-тестов | `test: add unit tests for engine hours estimation` |
| `chore:` | Настройка сборки, пакетов NuGet, .gitignore | `chore: add sqlite-net-pcl package to project` |

> 💡 **Правило золотого коммита:** один коммит — одно законченное логическое действие. Не делай коммит раз в неделю размером в 5 000 строк. Делай небольшие аккуратные коммиты по 1-3 раза за вечер работы.

## 7. Ветвление (Branches) — сердце Git

Представь реку. Главное русло называется `main`. В нём течёт **только стабильный, 100% рабочий код**.

Ты хочешь сделать новую рискованную функцию — сканирование одометра по Bluetooth ELM327. Ты не трогаешь `main`. Ты создаёшь ответвление (рукав реки) — ветку `feature/bluetooth-obd`.

```
          (ветка feature/bluetooth-obd)
               ┌─── коммит ─── коммит ───┐
               │                         ▼ (слияние merge)
─── коммит ────┴──────────────────────── коммит ────────────────► (ветка main)
```

### Команды для работы с ветками:

```bash
# 1. Посмотреть список всех веток (* отмечена текущая)
git branch

# 2. Создать новую ветку и сразу переключиться на неё:
git switch -c feature/engine-hours
# (Старый аналог этой команды: git checkout -b feature/engine-hours)

# 3. Спокойно работаем, пишем код, делаем коммиты...
git add .
git commit -m "feat: add engine hours model and formulas"

# 4. Переключиться обратно на основную ветку main:
git switch main

# 5. Влить изменения из нашей ветки в main (Merge):
git merge feature/engine-hours

# 6. Ветка выполнила свою задачу, её можно удалить:
git branch -d feature/engine-hours
```

## 8. Конфликты слияния (Merge Conflicts)

**Что это такое?**  
Представь: в ветке `main` ты изменил строку 15 в файле `Vehicle.cs` (написал дефолтный темп 35 км/день).  
А в ветке `feature/test` твой напарник (или ты сам вчера) в этой же строке 15 написал дефолтный темп 40 км/день.

Ты запускаешь `git merge`. Git видит, что **одна и та же строчка была изменена по-разному в двух ветках**. Git не знает, кто из вас прав, останавливает слияние и говорит: *«Конфликт! Человек, реши сам, какой вариант оставить»*.

### Как выглядит конфликт внутри файла:
Git прямо в твоем файле C# ставит метки:
```csharp
<<<<<<< HEAD (текущая ветка main)
public double DailyRate { get; set; } = 35.0;
=======
public double DailyRate { get; set; } = 40.0;
>>>>>>> feature/test
```

### Как решить конфликт:
1. Открой файл в Visual Studio или VS Code (Visual Studio сама подсветит конфликт красивыми кнопками: *"Accept Incoming"*, *"Accept Current"* или *"Accept Both"*).
2. Выбери правильный вариант и удали служебные маркеры `<<<<<<<`, `=======`, `>>>>>>>`.
3. Сохрани файл.
4. Выполни:
   ```bash
   git add Vehicle.cs
   git commit -m "merge: resolve conflict in DailyRate default value"
   ```
5. Конфликт решен! Это стандартная рутина программиста, бояться конфликтов не нужно.

## 9. Связка с облаком: GitHub, Remote, Push и Pull

Когда локальный репозиторий готов, пора отправить его в облако на GitHub.

### Шаг 1. Создай репозиторий на сайте GitHub
1. Зайди на [github.com](https://github.com) под своим логином.
2. Нажми зеленую кнопку **«New»** (Создать репозиторий).
3. Назови его, например, `AutoCareTracker`.
4. Сделай его **Public** (публичным — чтобы приемная комиссия могла его открыть).
5. **НЕ ставь галочки** на "Add README", ".gitignore" или "license", если у тебя уже есть локальная папка (иначе возникнут конфликты при первом пуше).
6. Нажми **«Create repository»**.

### Шаг 2. Привяжи локальную папку к GitHub
GitHub покажет подсказку с командами. Выполни их в терминале своей папки:

```bash
# 1. Привязываем удаленный сервер (remote) под именем 'origin':
git remote add origin https://github.com/ТВОЙ_ЛОГИН/AutoCareTracker.git

# 2. Убеждаемся, что главная ветка называется main:
git branch -M main

# 3. Отправляем (push) код на GitHub:
git push -u origin main
```
Флаг `-u` (upstream) связывает локальную ветку `main` с удаленной на GitHub. В следующий раз для отправки кода достаточно будет написать просто:
```bash
git push
```

### Как забрать свежие изменения из GitHub на компьютер (`git pull`):
Если ты редактировал код на другом компьютере или через веб-сайт GitHub:
```bash
git pull
```
`git pull` скачивает изменения из облака и автоматически соединяет их с твоей локальной папкой.

## 10. Pull Requests и Code Review

В профессиональной разработке **никто никогда не пушит код напрямую в `main`**.

Вместо этого используют процесс **Pull Request (PR)**:
1. Программист делает ветку: `feature/odometer-calibration`.
2. Пишет код и пушит эту ветку на GitHub:
   ```bash
   git push -u origin feature/odometer-calibration
   ```
3. На сайте GitHub нажимает кнопку **«Compare & pull request»**.
4. Открывается страница PR с описанием: *«Я добавил модальное окно калибровки пробега, проверьте пожалуйста»*.
5. Другие разработчики проводят **Code Review** (ревью кода): смотрят каждую строчку, оставляют комментарии, указывают на потенциальные баги.
6. Когда всё проверено, нажимается кнопка **«Merge pull request»**, и изменения вливаются в `main`.

> 💡 Для поступления: если ты оформишь 2-3 фичи своего проекта через Pull Requests (даже сам себе!), комиссия в университете увидит, что ты знаешь культуру командной разработки software engineering!

## 11. Файл .gitignore: санитария проекта

**Катастрофа новичков:** залить в Git 500 мегабайт мусора — скомпилированные файлы `.exe`, `.dll`, временные файлы Visual Studio, кэши и локальные базы данных.
Репозиторий раздувается, клонируется 10 минут, а чужие компьютеры не могут его скомпилировать из-за конфликта кэшей.

Файл **`.gitignore`** в корне проекта говорит Гиту: *«Эти файлы и папки НЕ замечай, никогда не добавляй их в коммиты»*.

Создай в корне своей папки файл с точным именем `.gitignore` (с точкой в начале) со следующим содержимым:

```gitignore
## Visual Studio временные файлы
.vs/
*.user
*.suo
*.userosscache
*.sln.docstates

## Результаты сборки C# (.NET)
[Bb]in/
[Oo]bj/
build/

## Локальные базы данных (чтобы не затереть базу другого пользователя)
*.db
*.sqlite
*.sqlite3
*.db-shm
*.db-wal

## Логи и дампы аварий
*.log
*.crash

## Операционные системы
.DS_Store
Thumbs.db
```

> ⚠️ **Важно:** файл `.gitignore` нужно создать **ДО** первого коммита `git add .`, чтобы мусорные файлы даже не попали в индекс.

## 12. Машина времени: исправление ошибок и откат

Что делать, если что-то пошло не так?

### 1. Я отредактировал файл, но всё испортил и хочу вернуть, как было в последнем коммите:
```bash
git restore Vehicle.cs
```
Файл мгновенно сбрасывается до состояния последнего сохранения.

### 2. Я случайно сделал `git add .`, но не хочу коммитить эти файлы прямо сейчас:
```bash
git restore --staged .
```
Файлы вынимаются из коробки (Staging), но сами изменения в коде не удаляются.

### 3. Я только что сделал коммит, но забыл дописать одну строчку или опечатался в сообщении:
```bash
# Добавь забытый файл:
git add missed_file.cs
# Добавь его в предыдущий коммит без создания нового:
git commit --amend -m "feat: correct commit message"
```

### 4. Временный карман: `git stash`
Представь: ты сидишь посреди сложной переделки метода, половина кода не компилируется. Вдруг звонит друг и говорит: *«Срочно покажи мне экран настроек, там баг!»*.  
Тебе нужно срочно переключить ветку, но с недоделанным некомпилируемым кодом Git переключиться не даст.
```bash
# Спрятать все текущие незакоммиченные изменения во временный "карман":
git stash

# Твоя папка стала кристально чистой! Переключайся куда угодно:
git switch main

# Позже вернулся назад и достал всё из кармана:
git stash pop
```

## 13. Работа с Git прямо в Visual Studio

Visual Studio имеет отличный встроенный визуальный интерфейс для Git, поэтому терминал нужен не всегда.

### Как пользоваться Git мышкой в VS:
1. **Окно «Git Changes» (Изменения Git):**
   * Меню: `View -> Git Changes` (Вид -> Изменения Git) или горячие клавиши `Ctrl + 0, Ctrl + G`.
   * Ты видишь список измененных файлов.
   * Нажатие на значок `+` рядом с файлом — это `git add`.
   * Поле сверху — для сообщения коммита.
   * Кнопка **«Commit All»** (Зафиксировать все) — делает коммит.
   * Кнопка со стрелочкой вверх ⬆️ — это `git push`.
   * Кнопка со стрелочкой вниз ⬇️ — это `git pull`.

2. **Просмотр разницы (Diff):**
   * Дважды кликни на любой измененный файл в окне Git Changes — Visual Studio откроет разделенный экран: слева старый код красным, справа новый код зеленым. Ты видишь каждую измененную букву!

3. **Переключение веток:**
   * В правом нижнем углу Visual Studio всегда написано название текущей ветки (например, `main`). Кликни на него — откроется меню, где в 1 клик можно создать новую ветку или переключиться на существующую.

## 14. Как оформить GitHub для поступления в китайский вуз (HIT / NUAA)

Для приемной комиссии (особенно для программ Software Engineering на английском) твой профиль GitHub — это **главное вещественное доказательство твоих навыков**. Аттестат показывает оценки, а GitHub показывает, умеешь ли ты реально создавать программные системы.

### 1. Твой профиль:
* **Аватарка:** аккуратное опрятное фото (не аниме и не мем).
* **Bio (О себе):** на английском языке:  
  *«High school student passionate about Software Engineering, C#, and Mobile Development. Aspiring CS student at HIT / NUAA 2028.»*
* **Pinned Repositories:** закрепи свой проект `AutoCareTracker` в самом верху профиля.

### 2. Зелёные квадратики активности (Contribution Graph):
Вузы обращают внимание на регулярность. Если все коммиты сделаны за одну ночь перед дедлайном — это выглядит подозрительно. Если график зеленый на протяжении полугода (коммиты 2-3 раза в неделю) — это доказывает твою дисциплину и постоянное развитие.

### 3. Идеальный файл `README.md` для проекта:
Файл `README.md` в корне репозитория — это «витрина» твоего проекта. Он должен быть **на английском языке** и содержать следующие разделы:

```markdown
# 🚗 AutoCare Tracker — Smart Car Maintenance & Wear Prediction App

An intelligent cross-platform mobile application built with **C#** and **Avalonia UI** that estimates vehicle mileage, calculates wear percentage of critical car components, and schedules predictive maintenance without requiring hardware OBD-2 scanners.

---

## 🌟 Key Features
- **Smart Odometer Interpolation:** Automatically estimates daily mileage and wear based on historical calibration points.
- **Engine Hours & Highway/City Mode:** Dynamic wear calculation based on driving tempo.
- **Wear Visualizer:** Color-coded status bars (Normal, Warning >85%, Overdue >100%).
- **Offline First:** Local high-performance storage using SQLite.

---

## 📐 Mathematical Model & Formulas
The application computes the daily driving tempo without constant GPS tracking:

$$\text{DailyRate} = \frac{\text{Mileage}_{\text{new}} - \text{Mileage}_{\text{old}}}{\Delta \text{Days}}$$

Dynamic component wear is evaluated as:
$$\text{Wear} = \max\left(\frac{\Delta \text{km}}{\text{Interval}_{\text{km}}}, \frac{\Delta \text{days}}{\text{Interval}_{\text{days}}}\right) \times 100\%$$

---

## 🛠 Tech Stack & Architecture
- **Language:** C# 12 / .NET 8
- **UI Framework:** Avalonia UI (Cross-Platform: Android, Windows)
- **Architecture:** MVVM Pattern with `CommunityToolkit.Mvvm`
- **Database:** SQLite + Entity Framework Core

---

1. Clone the repository:
   ```bash
   git clone https://github.com/YourUsername/AutoCareTracker.git
   ```
2. Open `AutoCareTracker.sln` in **Visual Studio 2022+**.
3. Select `CarTrackerApp.Desktop` or `CarTrackerApp.Android` and press **F5 (Run)**.

## 15. Шпаргалка по всем командам Git

| Команда | Что делает |
|---|---|
| `git init` | Инициализировать новый репозиторий в текущей папке |
| `git clone <url>` | Скачать существующий репозиторий из интернета |
| `git status` | Показать состояние файлов (что изменено, что готово к коммиту) |
| `git diff` | Показать изменения в коде построчно |
| `git add <файл>` | Положить файл в коробку подготовки (Staging) |
| `git add .` | Положить ВСЕ измененные файлы в Staging |
| `git commit -m "msg"` | Зафиксировать снимок с комментарием |
| `git commit --amend` | Дополнить последний коммит забытыми файлами |
| `git log --oneline` | Показать историю коммитов в компактном виде |
| `git branch` | Показать список локальных веток |
| `git switch -c <name>` | Создать новую ветку и перейти в неё |
| `git switch <name>` | Переключиться на существующую ветку |
| `git merge <name>` | Влить указанную ветку в текущую |
| `git branch -d <name>` | Удалить ветку (после слияния) |
| `git remote add origin <url>` | Привязать локальный проект к репозиторию на GitHub |
| `git push -u origin main` | Отправить коммиты на GitHub (в первый раз) |
| `git push` | Отправить свежие коммиты на GitHub |
| `git pull` | Скачать и влить свежие изменения с GitHub |
| `git restore <файл>` | Сбросить изменения в файле до последнего коммита |
| `git restore --staged <файл>`| Вынуть файл из Staging (отменить `git add`) |
| `git stash` | Спрятать незакоммиченную работу во временный карман |
| `git stash pop` | Достать работу из кармана обратно |
